# 현행 분석

## 코드 구조
- 백엔드 `backend/app.py`
  - 엔드포인트: `/api/health`, `/api/config`, `/api/folders`, `/api/emails/<path>`, `/api/email/<path>/<file>`, `/api/attachment/...`, `/api/stats`
  - 설정 파일 `config.json` 로컬 유지
  - 전역 `EMAIL_ROOT` 의존, 폴더 순회 시 `.eml` 필터
  - 보안: CORS 허용 범위 설정, 응답 후크에서 와일드카드(`*`)도 추가됨
  - 로깅 존재(기본 INFO)
- 파서 `backend/email_parser.py`
  - 헤더/본문/첨부 추출 구현 양호, MIME/인코딩 예외 대비 있음
  - 본문 HTML → 텍스트 간이 변환
- 모델 `backend/models.py`
  - SQLite 직접 접근, 태그/연결/인덱스/설정/상태 테이블 정의
  - 검색 인덱스 테이블은 있으나 실제 API에서 적극 활용은 제한적
- 실행 `run.py`
  - 요구사항 검사/의존성 설치/동시 구동 스크립트

## 장점
- 단순하고 이해 쉬운 구조, 빠른 온보딩 가능
- 파서의 예외 처리와 본문/첨부 추출 로직이 실용적
- 로컬 전용 실행으로 보안 노출면적이 작음

## 한계/개선점
- 검색 성능: 전체 파일 순회 + 본문 파싱은 대용량에서 느림 → FTS 인덱스 필요
- 파일 경로 보안: 경로 조합 시 정규화/루트 제한 강화 필요
- 설정/상태/태그 API 부재: 모델은 있으나 REST 엔드포인트 미정의
- CORS 설정 중복 및 와일드카드 허용 → 최소권한 원칙 위반 가능
- 로깅/감사/장애복구 시나리오 정립 필요
- 테스트/품질관리 체계 부재(pytest/RTL/e2e 등)
- 배포: CRA 및 Flask 이원 실행 → 단일 실행/패키징 옵션 제공 필요

## 사용 시나리오 관찰
- 최초 설정에서 `email_root` 지정 → 폴더/이메일/보기/검색
- 첨부 다운로드는 파일명 기반, 경로 계산 로직에 취약점 가능성
